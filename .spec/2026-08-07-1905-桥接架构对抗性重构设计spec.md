## 0. 摘要（一句话）

**保留我方 L2/L3/L4 全部精华（Outbox 可靠投递、权限桥、会话编排、定时任务路由、菜单/help 卡片），外科手术式改造 L1/L0 连接层**——从"强制重建者"转向"观察者 + 卫生契约 + 配额保护"，吸收参考项目之精华（AX1202 薄 daemon、zxsctxx SDK 原生重连回调），弃其糟粕（我方 supervisor 状态机、AX1202 无 Outbox 的丢回复）。

> 上版 spec（1835）的错误：把方案整体推倒重抄 AX1202。用户实测 AX1202"总是收不到 pi 回复"——已从源码证实其根因。**推翻重抄是错的，外科手术是对。**

## 1. 对抗性复盘（谁也别吹）

### 1.1 攻击我方现有架构（找出糟粕）

| 攻击点 | 证据 | 判定 |
| -------- | ------ | ------ |
| **ConnectionSupervisor 静默重建**：20min 无事件 → 无条件重建连接 | `connection-supervisor.ts` L1-3：`silence beyond silenceSuspectMs triggers rebuild`。健康连接在"没人说话"时也会被误杀 | ❌ **事故根因**。重建 = 新 WS = 连接变动 = 烧租户配额 |
| **周期性 REST 探针**（30s） | `permission-probe.ts` 定时 `GET /bot/v3/info` | ❌ 不 reset 静默计时，纯制造噪音；连接健康不由 REST 决定 |
| **退避重试循环**（1s→60s） | `reconnectBackoffBaseMs/MaxMs` | ❌ 与 SDK 自带 autoReconnect 重复且互相打架 |
| **missed-compensation（断连补收）** | 断连期间消息丢失的补偿 | ✅ 有价值（配合稳定连接使用）；非 churn 源 |
| **Outbox（at-least-once + 幂等键）** | `outbox.ts`，持久可靠道 | ✅ **核心精华**。AX1202 没有它所以丢回复 |
| **权限桥（工具审批卡）** | `permission-bridge.ts` + `tool-call-gate.ts` | ✅ **独有精华**。AX1202/zxsctxx 都没有 |
| **会话隔离（per-key AgentSession + FIFO）** | `conversation-manager.ts` | ✅ 精华 |
| **定时任务路由（scheduler → 飞书）** | `bridge-runtime.ts` + `outbound-router.ts` | ✅ 精华，用户明确要求 |
| **菜单/help 命令卡** | `command-controller.ts`（help/status/new/resume/model/stop） | ✅ 精华，用户明确要求 |
| **任务状态卡 / 实时状态** | `turn-supervisor.ts` + cards | ✅ 精华 |

### 1.2 攻击 AX1202（参考项目中最流行的，用户实测其丢回复）

| 攻击点 | 源码证据 | 判定 |
| -------- | --------- | ------ |
| **出站无 Outbox，内存直发** | `delivery.ts`：`send() → im.message.reply/create` 直接 REST，无队列、无持久化、无跨重启重试 | ❌ **"收不到回复"根因之一**：daemon 中途死亡/网络瞬断即丢 |
| **会话路由绑定丢失即丢回复** | `bridge-store.ts` 内存 Map，session 重建后 job→chat 绑定丢失 | ❌ "收不到回复"根因之二 |
| **单体 index.ts 600+ 行** | 命令/状态/守护/清理全部挤在一个文件 | ❌ 可维护性差 |
| **薄 daemon（pi --mode rpc -e ext）** | `index.ts` daemonSpec() | ✅ 精华：daemon 只是扩展的另一个运行环境，无状态机 |
| **gateway lock 仅去重**（30s 过期/5s 心跳/token 防抢占） | `gateway-lock.ts` | ✅ 精华：简单、防双连接 |
| **SDK 原生重连（无 supervisor）** | transport 只有 start/stop + fire-and-forget | ✅ 精华：重连交给 SDK 服务端驱动退避 |
| **功能面**：续聊/切模型/附件/状态卡 | 已有 | ✅ 我方已有同类或更优（权限桥是增量） |

### 1.3 攻击 zxsctxx（pi-feishu-bridge，CardKit 流式）

| 攻击点 | 证据 | 判定 |
| -------- | ------ | ------ |
| **in-process 无 daemon** | `src/index.ts` 直接 pi.on 注册 | ❌ 无 24/7 能力，pi 重启即断——不满足我方"桥独立运行"需求 |
| **WSClient 显式 `autoReconnect:true` + 四回调**（onReady/onReconnecting/onReconnected/onError） | `feishu-client.ts` L247-280 | ✅ 精华：**SDK 原生重连 + 状态回调**，这是连接层的正确姿势 |
| **`wsConfig.pingTimeout:30`** | 同上 | ✅ 精华：僵尸检测交给 SDK 心跳，不自研 |
| **分层清晰（src/ 按域分模块 + 全面测试）** | streaming/ access/ feishu/ commands/ clarify/ queue | ✅ 精华：结构可借鉴 |
| **CardKit v2 流式输出** | streaming/card-manager.ts | ⚠️ 本次不做（大复杂度，无需求）；列为未来可选项 |

### 1.4 对抗结论

- **错误认知**："SDK 重连不可信，要自研 supervisor"（原 spec ADR-2/ADR-12）→ **实机证明恰恰相反**：SDK 自带 `pingTimeout` 心跳僵尸检测 + 服务端驱动退避重连，是经过数万用户验证的；自研 supervisor 的重建风暴才是灾难源。
- **错误认知**："连接稳定后 missed-compensation 不再需要"（上版 spec 删表）→ 错。断连补收配合 SDK 自动重连是**互补**的：SDK 负责"重连"，我们负责"重连期间的消息不丢"。
- **正确认知**：连接层要做的不是"监控并干预"，而是**"观察 + 报告 + 卫生 + 保护"**——观察 SDK 状态回调，报告给用户，保证优雅关闭，用重启预算保护租户配额。

## 3. 目标架构

### 3.1 总形态（L0-L4，标注改造点）

```
┌─────────────────────────── pi TUI 进程 ───────────────────────────┐
│ L4 呈现：cards / rich-text / task-status-card（不动）              │
│ L3 出站：Outbox / LiveChannel / OutboundRouter（不动）             │
│ L2 编排：ConversationManager / PermissionBridge / TurnSupervisor   │
│          / BridgeRuntime(定时任务) / EventForwarder（不动）        │
│ L1 接入：transport（✅ 改造：SDK 原生重连 + 回调状态）             │
│          InboundPipeline / missed-compensation（保留）             │
│ L0 宿主：daemon-host（✅ 瘦身）+ gateway-lock（仅去重）            │
└───────────────────────────────┬────────────────────────────────────┘
                                │ spawn（detached，pi --mode rpc -e ext）
                                ▼
┌─────────────────────────── 薄 daemon（同一扩展代码）──────────────┐
│ 同一份 index.ts + transport + L2/L3/L4 全部复用                   │
│ lock 单 owner 去重（5s 心跳 / 30s 过期 / token 防抢占）            │
└───────────────────────────────────────────────────────────────────┘
```

**核心不变式：扩展代码只有一份，TUI 与 daemon 是它的两个运行环境（AX1202 模式）。**

### 3.2 L1 连接层新设计（本次重构的核心创新）

**范式转变：从"强制重建者" → "观察者 + 卫生 + 保护"。**

```ts
// transport.start() 目标形态（抄 zxsctxx 姿势 + 我方状态语义）
this.wsClient = new sdk.WSClient({
  appId, appSecret,
  domain,                                   // 恢复显式 domain（上版误删，参考实现全都在传）
  autoReconnect: true,                      // SDK 服务端驱动退避重连
  wsConfig: { pingTimeout: 30 },            // SDK 内置僵尸检测：服务端 ping 无 pong → onError
  loggerLevel: sdk.LoggerLevel.error,
  onReady:        () => status.on("connected"),
  onReconnecting: () => status.on("connecting"),
  onReconnected:  () => status.on("connected"),
  onError:        (e) => status.on("error", e.message),
});
this.wsClient.start({ eventDispatcher: dispatcher });   // fire-and-forget，SDK 内部管一切
```

**三个创新点（参考项目没有的）：**

**① 连接卫生契约（graceful close contract）**

```
任何停止路径（/feishu stop、SIGTERM、卸载自监控退出）必须：
  1. 先 wsClient.stop()（发关闭帧，服务端不留死连接）
  2. 再释放 gateway lock
  3. 进程树 SIGTERM 逐层（严禁 kill -9）
调试纪律：restart 后观察 ≥10 分钟；一次只验证一个变量。
```

**② 重启预算治理（quota governor）——防止任何人（含操作者自己）再烧穿配额**

```
新增 QuotaGovernor（src/inbound/quota-governor.ts，纯函数 + 单测）：
  - 记录最近连接尝试时间戳（内存 + 落盘 ~/.pi/agent/feishu-link/conn-history.jsonl）
  - 规则：60 分钟内连接尝试 ≥ N（默认 12）→ 拒绝新 start，提示"连接配额保护已触发，
    请等待 X 分钟"；/feishu status 显示今日尝试数
  - daemon 的 SDK autoReconnect 重试不计入（那是维持存量连接，非新建）
```

> 这是对本次事故的直接防御：配额烧穿从"事故"变成"不可能"。

**③ 观察者状态总线（不再有状态机）**

```
状态唯一来源 = lock owner（是否在跑）+ transport 回调（连接健康）。
删除 connection-status.ts 的状态机事件体系（若与回调冗余）。
断连/恢复由 SDK 回调驱动 → NotificationThrottler 合并后通知用户
（"连接已断开，正在自动重连…" / "连接已恢复，期间入站消息已补收"）。
```

**保留**（配合稳定连接使用，非 churn 源）：

- `missed-compensation.ts`：SDK 重连期间丢失的入站消息，恢复后主动拉取补收
- `InboundPipeline` 去重：防重放

### 3.3 L0 宿主层（薄 daemon）

- `daemon-host.ts` 瘦身为 AX1202 模式：
  - spawn：`pi --mode rpc --no-extensions --no-skills --no-themes --no-prompt-templates --no-context-files --no-builtin-tools -e <extension>`
  - 启动成功判定：检测到新存活 lock owner（保留我方 0.1.3 修复）
  - **删除**：status.json 状态机写入、RPC 消息协议（如与 lock 冗余）、进程健康心跳上报
- `gateway-lock.ts`：保留单 owner 去重语义（token 防抢占 + 30s 过期 + 5s 心跳），不扩展成状态机
- 卸载自监控（0.1.4 实现）：保留——它是卫生契约的一部分

### 3.4 L2/L3/L4：不动（列明理由）

| 模块 | 为什么不动 |
| ------ | ----------- |
| Outbox | AX1202 丢回复的根治。at-least-once + 幂等键 + 分航道并行（ADR-3/9/10） |
| LiveChannel | 流式展示优化，正确性不依赖它（ADR-8） |
| OutboundRouter | 定时任务通用路由抽象（ADR-4，用户明确要求） |
| PermissionBridge + ToolCallGate | 我方独有，headless 会话审批必须有主（ADR-11） |
| ConversationManager | per-key 会话隔离 + FIFO + 恢复（ADR-6） |
| TurnSupervisor | 回合超时/卡死中止（用户价值） |
| BridgeRuntime | 定时任务 marker 捕获 → 路由绑定（已实现 0.1.1 修复） |
| CommandController | help/status/new/resume/model/stop —— **机器人菜单增强面** |
| cards/rich-text/attachments | 呈现与附件（用户价值） |

### 3.6 机器人菜单实现说明（2026-08-07 已完成）

**飞书侧事实**（官方文档实读）：
- 菜单只在开发者后台配置（**无 OpenAPI**）：添加应用能力 → 机器人 → 机器人自定义菜单 → 开启 → 创建版本发布（等 5 分钟）
- 仅单聊展示；两种样式：可切换（≤3×5）/ 悬浮（≤5×10，V7.22+）
- 三种动作：跳转链接 / 发送文字消息（V7.22+，文案当消息发）/ **推送事件**（订阅 `application.bot.menu_v6`，`event_key` 为唯一标识）

**实现（双通道，全部走既有命令管线）**：
1. **推送事件通道**（推荐，全版本）：`transport.ts` 注册 `application.bot.menu_v6` → `parseBotMenuEvent`（兼容 schema2.0 与拍平结构）→ `index.ts handleBotMenuEvent`：event_key → 命令文案 → 合成 FeishuInboundMessage（`replyViaOpenId` 标记）→ 走 `handleCommand`
2. **回复路径**：菜单事件无 chat_id → 无既有路由时先按 open_id 占位发送取 chat_id 绑定路由（`sendMessageByOpenId` 返回 `{messageId, chatId}`）；`replyTo` 增加 `replyViaOpenId` 兜底直发
3. **发送文字消息通道**（V7.22+）：菜单文案直接填 `/status` 等 → 普通消息 → 现有管线，零新代码
4. **订阅自检**：`checkEventSubscription` 覆盖两个必需事件；setup 引导文案 `buildMenuGuideText` 输出配置路径 + 推荐菜单结构

**新增文件**：`src/inbound/bot-menu.ts`（纯函数，7 项单测）；改造：transport/auth-setup/index.ts/types.ts。测试 216 → 226。

## 4. 对抗性验证表（每个失败模式 × 对策）

| 失败模式 | 谁可能触发 | 对策（对应机制） |
| ---------- | ----------- | ----------------- |
| 配额再烧穿（exceed_conn_limit） | 操作者反复 restart / 多实例抢占 | QuotaGovernor 60min/12 次熔断 + lock 单 owner + 卫生契约 |
| WS 僵尸（TCP 活着但事件不通） | 网络代理/防火墙 | SDK `pingTimeout:30` 心跳 → onError → autoReconnect（不再靠"静默 20min"误杀健康连接） |
| 健康连接被"静默"误杀 | 长时间无人发消息 | ❌ 已删除静默重建逻辑；静默 = 正常 |
| SDK 重连失败（服务端持续拒绝） | 租户配额临时锁死 | SDK 服务端退避（~120s/次）自然降温；QuotaGovernor 提示用户停止操作等待 |
| 回复丢失（AX1202 的用户痛点） | daemon 中途死亡/网络瞬断 | Outbox 持久化 at-least-once + 跨重启重试 + 幂等键 |
| 定时任务结果丢失 | scheduler 到点但 daemon 正在重启 | Outbox kind:"scheduled" 持久道 + deliverOnce 幂等 |
| 断连期间入站消息丢失 | SDK 重连窗口 | missed-compensation 恢复后补收 |
| 双实例抢连接 | 两个 TUI 都 /feishu start | gateway lock token 防抢占，第二个返回 busy |
| 权限审批真空（headless 会话调危险工具） | 飞书消息触发、无人在 TUI 确认 | PermissionBridge 审批卡（我方独有） |
| 卸载后旧 daemon 占连接 | pi remove | 卸载自监控（0.1.4）→ 释放 lock + 退出 |

## 7. 风险与缓解

| 风险 | 缓解 |
| ------ | ------ |
