## 1. 背景与问题

### 1.1 事故回顾

2026-08-07 全天调试 pi-feishu-link 桥接消息投递失败，最终定位到：

- **表面症状**：所有飞书应用的新 WS 连接被拒，`exceed_conn_limit (1000040350)`。
- **直接原因**：租户连接配额被大量未正常关闭的 WS 连接耗尽（SIGKILL 残留 + 频繁重连）。
- **根本原因（本次 spec 要解决的）**：**pi-feishu-link 自研的 daemon + supervisor 连接管理机器过度复杂，本身就是连接变动的制造者**。

### 1.2 必须回答的问题

1. 别人（社区 5 个同类项目）是怎么实现飞书桥接的？
2. 哪种架构最优雅、资源占用最小、可维护性最高、最现代？
3. pi-feishu-link 应重构为哪种架构？保留哪些、删除哪些？

## 3. 自顶向下分析

### 3.1 五类架构总览

```
┌────────────────────────────────────────────────────────────────────┐
│ 方案 A：纯 in-process extension（zxsctxx/pi-feishu-bridge）        │
│   pi 进程 ── WSClient（SDK 自带 autoReconnect）                     │
│   无 daemon、无锁、无 supervisor。pi 重启 = 桥重启。                │
├────────────────────────────────────────────────────────────────────┤
│ 方案 B：薄 daemon + extension（AX1202/pi-feishu-lark，最流行）      │
│   pi TUI ──spawn──▶ pi --mode rpc 薄 daemon ── WSClient            │
│   gateway lock（仅单 owner 去重）+ 2s 状态刷新。无 supervisor。      │
├────────────────────────────────────────────────────────────────────┤
│ 方案 C：官方 CLI 子进程（Naoki326/pi-lark-notify）                  │
│   pi 进程 ──spawn──▶ lark-cli event consume 子进程                  │
│   零自研 WS 代码，官方 CLI 管连接。                                 │
├────────────────────────────────────────────────────────────────────┤
│ 方案 D：官方 CLI skill 包装（TungLamC/pi-lark-cli）                 │
│   纯 skill，无常驻连接。                                            │
├────────────────────────────────────────────────────────────────────┤
│ 方案 E：重型 daemon + supervisor（**现状 pi-feishu-link**）         │
│   daemon + gateway lock + status.json + connection-supervisor      │
│   （静默检测 20min/30s REST 探针/退避重试/降级报告）+ missed-        │
│   compensation + permission-probe + 进程树清理 + RPC CLI            │
└────────────────────────────────────────────────────────────────────┘
```

### 3.2 关键事实（代码证据）

**① 没有任何一个参考项目有 connection-supervisor**

- AX1202 的 transport 核心就三行：

  ```ts
  this.wsClient = new lark.WSClient({ appId, appSecret, domain, loggerLevel });
  this.running = true;
  this.wsClient.start({ eventDispatcher: dispatcher });  // fire-and-forget
  ```

- 全仓库无 `setInterval` 探针、无 `silence` 检测、无 supervisor 文件（仅 status 刷新 timer）。
- zxsctxx 显式 `autoReconnect: true` + `onReady/onReconnecting/onReconnected/onError` 回调，其余全交给 SDK。

**② daemon 本身不是问题，问题的重量级**

- AX1202 也有 daemon（卖点"Pi agent 关闭后仍可对话"），但它是**薄 daemon**：
  `pi --mode rpc --no-extensions --no-skills --no-themes --no-builtin-tools -e <extension>`
  即"一个只跑扩展的 pi rpc 会话"，代码即扩展本身，无额外状态机。
- gateway lock 只做**单 owner 去重**（30s 过期、5s 心跳），不做状态机。
- 我的 daemon 额外叠加了：status.json、supervisor 状态机、missed-compensation、permission-probe、connection-status 事件体系——全部是自研机器。

**③ SDK 自带的重连是"服务端驱动退避"，不是风暴**

- SDK autoReconnect 的间隔由服务端 `pullConnectConfig` 下发（默认 ~120s）。
- 我此前观察到的"每 ~6s 一次拒绝"**不是 SDK 内部重试**，而是**我的 supervisor 每 ~15s 静默重启 transport，每次 restart = new WSClient = 新连接尝试**。风暴源头是 supervisor 自己。

**④ 我误判的"domain 会破坏投递"是错的**

- AX1202、zxsctxx 全部显式传 `domain`（`lark.Domain.Feishu` / `lark.Domain.Lark`）且工作正常。
- 我早前移除 domain 的结论无实机依据，属误判。

## 4. 架构选型结论

### 4.1 推荐：方案 B（薄 daemon + extension，AX1202 模式）

理由：

1. **被社区验证**：AX1202 是同类中用户量最大的实现，模式经大量实机使用考验。
2. **满足用户既有需求**：pi-feishu-link 原始需求就是"pi 关闭后桥接仍常驻"（daemon 能力），方案 A 不满足，方案 B 用最低复杂度满足。
3. **可维护性最高**：没有 supervisor 状态机 = 没有状态机 bug；连接健康全权交给 SDK 自带 autoReconnect（服务端驱动退避，天然防风暴）。
4. **删除即修复**：本次事故的直接根因（连接变动烧配额）随 supervisor 删除而消失。

### 4.2 否决的选项

- **方案 A 纯 in-process**：资源最省但失去 daemon 能力，不符合用户"桥接独立于 pi 运行"的需求。
- **方案 C 官方 CLI**：功能上限低（无法做卡片、流式、群策略等定制），且依赖外部 CLI 的演进节奏。
- **维持现状（方案 E）**：继续背负 supervisor 状态机，事故会重演。

### 4.3 不采纳的部分

- zxsctxx 的 CardKit v2 流式卡片（7,650 LOC 中大半是流式/监控/访问控制）：本次需求未要求流式输出，引入会再次放大复杂度。列为未来可选项。

## 5. 目标架构详细设计

### 5.1 总体形态

```
┌─────────────────────────── pi TUI 进程 ───────────────────────────┐
│  extension index.ts（同一份代码）                                  │
│   · /feishu setup/start/stop/restart/status 命令                   │
│   · spawn 薄 daemon（pi --mode rpc --no-extensions -e <ext>）      │
│   · 2s 状态刷新（isRunning() + lock owner）                        │
│   · 消息端（pi session 消息 → 发送到飞书）                         │
└──────────────────────────────┬─────────────────────────────────────┘
                               │ spawn（detached）
                               ▼
┌─────────────────────────── 薄 daemon（pi rpc 会话）───────────────┐
│  同一 extension 代码                                              │
│   · transport.start() → WSClient（SDK autoReconnect）              │
│   · gateway lock：单 owner 去重（5s 心跳 / 30s 过期）              │
│   · inbound：im.message.receive_v1 → 会话注入 → 回复               │
│   · outbound：delivery（消息/图片/文件/卡片/reaction）             │
└───────────────────────────────────────────────────────────────────┘
```

### 5.2 连接策略（核心变更）

```ts
// 目标（抄 zxsctxx + AX1202 的合并写法）
this.wsClient = new sdk.WSClient({
  appId, appSecret,
  domain,                                  // 恢复显式 domain（之前误删）
  autoReconnect: true,                     // SDK 自带重连，服务端驱动退避
  onReady:        () => setStatus("connected"),
  onReconnecting: () => setStatus("connecting"),
  onReconnected:  () => setStatus("connected"),
  onError:        (e) => setStatus("error", e.message),
});
this.wsClient.start({ eventDispatcher: dispatcher });  // fire-and-forget
```

**明确禁止**：

- ❌ 静默检测（20min 无事件就重建）——健康连接也会因"没人说话"被误杀
- ❌ 周期性 REST 探针——探针不 reset 静默计时，纯制造连接噪音
- ❌ supervisor 重启状态机——SDK 自带重连已经做了
- ❌ 自研退避循环——SDK 的服务端驱动退避（~120s）天然防风暴

### 5.3 文件清单（目标态）

**保留（功能代码，逻辑基本不动）**

| 文件 | 说明 |
| ------ | ------ |
| `src/inbound/transport.ts` | 改为方案 B 连接策略（删 autoReconnect:false、isConnected 轮询） |
| `src/inbound/group-trigger.ts` | 群聊策略 |
| `src/inbound/attachment-pipeline.ts` | 附件收发 |

| `src/outbound/*` | 发送通道（delivery） |
| `src/sessions/*` | 会话管理（conversation-manager） |

**改造（瘦身）**

| 文件 | 变更 |
|------|------|
| `src/host/daemon-host.ts` | 改为 AX1202 薄 daemon（pi --mode rpc -e ext），删 RPC/status 消息协议，状态直接读 lock + isRunning |
| `src/host/gateway-lock.ts` | 保留单 owner 去重语义，删状态机化用法 |

**删除（本次事故的根源机器）**

| 文件 | 理由 |
| ------ | ------ |
| `src/inbound/connection-supervisor.ts` | 静默重建 + 探针 + 退避，全部删除，重连交给 SDK |
| `src/inbound/permission-probe.ts` | 探针体系的一部分 |
| `src/inbound/missed-compensation.ts` | 连接变动时代的补偿逻辑，连接稳定后不再需要 |
| `src/common/connection-status.ts` | 状态事件体系简化为 transport 回调 + lock owner |
| `src/index.ts` 中 supervisor/RPC 相关分支 | 同步删除 |

### 5.4 生命周期

```
/feishu setup  → 扫码 → 写 config → startDaemon()（若 autoStart）
/feishu start  → spawn 薄 daemon（幂等：lock busy 则提示已有 owner）
daemon 启动    → extension 初始化 → transport.start() → lock.update("connected")
WS 断线        → SDK autoReconnect（服务端退避）→ onReconnecting/onReconnected
/feishu stop   → SIGTERM daemon → 优雅 stop() → lock 释放 → 进程树清理
pi 重启        → daemon 不受影响，桥接继续
```

### 5.5 事故防范（连接卫生）

1. **禁止 kill -9 daemon**：stop 必须走 SIGTERM → 优雅 `wsClient.stop()`（发关闭帧），避免服务端残留死连接。
2. **重启频率纪律**：调试时一次 `restart` 后先观察 ≥10 分钟，不再"测一下重启一下"。
3. **单 owner 去重**：lock busy 时新 start 直接提示，不抢、不建第二条连接。
4. **连接计数自检**：`/feishu status` 增加"今日连接尝试次数"提示（可选，便于诊断）。

## 6. 迁移步骤

1. 写测试先行（TDD）：transport 新连接策略单测（onReady/onError 回调驱动状态）；daemon-host 薄 daemon 化单测。
2. 删 connection-supervisor / permission-probe / missed-compensation / connection-status，跑通全量测试。
3. transport 改连接策略（恢复 domain、autoReconnect:true、回调状态）。
4. daemon-host 改薄 daemon（AX1202 模式），status.json 协议下线。
5. index.ts 命令面瘦身（start/stop/restart/status/setup/debug/autostart/reset）。
6. 租户配额冷却后（≥1h 零连接）实机验证：setup → start → 发消息 → 收消息 → 停 → 再 start 一次（验证去重锁）→ 不再有第 3 次 start。

## 7. 验收标准

- [ ] 全量测试通过（预期 LOC 从 13,178 降到 ~6,000，文件从 32 降到 ~22）
- [ ] `git grep -r "silence\|probe\|supervisor" src/` 无连接管理残留
- [ ] 实机：setup 后一次 start，消息双向秒达；WS 断线（拔网线/杀进程模拟）后 SDK 自动重连，状态回调正确
- [ ] 连续 2 小时静默（无人发消息）后连接不被重建（无 churn），再发消息仍秒达
- [ ] 并发两个 /feishu start：第二个返回 busy，不建第二条连接
- [ ] /feishu stop 后 `lsof` 无残留 WS/进程
- [ ] pi 重启后 daemon 存活，消息继续可达

## 8. 风险与缓解

| 风险 | 缓解 |
| ------ | ------ |
| SDK autoReconnect 在极端场景（租户配额锁死）会持续退避重试 | SDK 退避 ~120s/次，影响可控；配合"停止一切连接等冷却"的运维纪律 |
| 删除 supervisor 后 WS 假死（心跳断但 TCP 在）无法感知 | SDK 自带 pingTimeout（zxsctxx 用 30s）；真断线 onError 触发重连 |
| 薄 daemon 与 TUI 扩展代码同源，改动需双环境验证 | 保持 extension 为唯一入口（与 AX1202 相同），daemon 仅是多一个运行环境 |
